## Summary

Defines the `start_checkpoint_competition` method that transitions a competition from `Pending` to `Collecting`, enabling checkpoint submissions. The method enforces that the epoch phase is `Checkpoint` and that the competition has not already been started.

## Specification

```rust
impl CheckpointCompetition {
    pub fn start_checkpoint_competition(&mut self) -> Result<()> {
        // 1. Verify phase == Checkpoint (return PhaseMismatch otherwise)
        // 2. Verify status == Pending (reject if already started)
        // 3. Transition status to Collecting
        Ok(())
    }
}
```

- MUST verify that the current epoch phase is `Checkpoint`. If the phase does not match, MUST return `PhaseMismatch` error.
- MUST verify that the current `status` is `Pending`. If the competition has already been started (status is not `Pending`), MUST reject the call.
- MUST transition `status` from `Pending` to `Collecting` on success.

## Acceptance Criteria

- [ ] Returns `Ok(())` and transitions to `Collecting` when phase is `Checkpoint` and status is `Pending`.
- [ ] Returns `PhaseMismatch` error when phase is not `Checkpoint`.
- [ ] Rejects (returns error) when status is already `Collecting`.
- [ ] Rejects (returns error) when status is `WinnerSelected`.
- [ ] Rejects (returns error) when status is `Finalized`.
- [ ] Rejects (returns error) when status is `Failed`.

## Implementation Notes

- The phase check ensures competitions only start during the designated checkpoint window.
- This is a guard transition: it only changes `status`, no other fields are modified.
- The method requires `&mut self` since it modifies internal state.
