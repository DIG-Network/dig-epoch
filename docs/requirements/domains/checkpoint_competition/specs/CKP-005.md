# CKP-005: Competition Lifecycle

> **Authoritative requirement:** [NORMATIVE.md](../NORMATIVE.md)
> **Verification:** [VERIFICATION.md](../VERIFICATION.md)
> **Tracking:** [TRACKING.yaml](../TRACKING.yaml)
> **Spec reference:** [SPEC.md - Section 3.10](../../../../resources/SPEC.md)

## Summary

Defines the complete competition lifecycle as a validated state machine. The competition progresses through a defined sequence of states, with each transition guarded by preconditions. Two terminal states exist: `Finalized` (success) and `Failed` (timeout or error).

## Specification

### State Machine

```
Pending ──► Collecting ──► WinnerSelected ──► Finalized
                │                 │
                │                 ▼
                └───────────► Failed
```

### Valid Transitions

| From            | To              | Trigger                                          |
|-----------------|-----------------|--------------------------------------------------|
| `Pending`       | `Collecting`    | `start_checkpoint_competition()` during Checkpoint phase |
| `Collecting`    | `WinnerSelected`| First valid `submit_checkpoint()` with positive score |
| `WinnerSelected`| `WinnerSelected`| `submit_checkpoint()` with higher score (leader update) |
| `WinnerSelected`| `Finalized`     | `finalize_competition(l1_height)`                |
| `Collecting`    | `Failed`        | Timeout or error during collection               |
| `WinnerSelected`| `Failed`        | Timeout or error before finalization              |

### Invalid Transitions

Any transition not listed above MUST be rejected. Specifically:

- `Pending` MUST NOT transition directly to `WinnerSelected`, `Finalized`, or `Failed`.
- `Collecting` MUST NOT transition directly to `Finalized`.
- `Finalized` MUST NOT transition to any other state (terminal).
- `Failed` MUST NOT transition to any other state (terminal).

### Lifecycle Invariants

- A new `CheckpointCompetition` MUST be created in `Pending` state with the epoch number.
- The `submissions` vector MUST be empty at creation.
- `current_winner` MUST be `None` at creation.
- Once `Finalized`, the competition is immutable.
- Once `Failed`, the competition is immutable.

## Acceptance Criteria

- [ ] Competition is created in `Pending` state with correct epoch.
- [ ] `Pending` -> `Collecting` transition works via `start_checkpoint_competition`.
- [ ] `Collecting` -> `WinnerSelected` transition works on first valid submission.
- [ ] `WinnerSelected` -> `WinnerSelected` transition works on higher score submission.
- [ ] `WinnerSelected` -> `Finalized` transition works via `finalize_competition`.
- [ ] `Collecting` -> `Failed` transition works on timeout/error.
- [ ] `WinnerSelected` -> `Failed` transition works on timeout/error.
- [ ] `Finalized` rejects all further transitions (terminal state).
- [ ] `Failed` rejects all further transitions (terminal state).
- [ ] Invalid transitions (e.g., `Pending` -> `Finalized`) are rejected.

## Implementation Notes

- The state machine is enforced by precondition checks in each method, not by a separate state machine engine.
- `WinnerSelected` -> `WinnerSelected` is a self-transition that updates the winner data when a higher score is submitted.
- Terminal states (`Finalized` and `Failed`) are enforced by rejecting all method calls that would modify state.
- The `Failed` state may be triggered by external timeout detection or internal error conditions.
