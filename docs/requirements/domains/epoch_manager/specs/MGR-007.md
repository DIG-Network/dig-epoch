## Summary

Defines the invariants for epoch history management within `EpochManager`. Completed epochs are archived as `EpochSummary` records in an append-only ordered collection. This history is the source of truth for all historical epoch queries.

## Specification

### Archive Behavior

When `advance_epoch()` is called (MGR-004), the current `EpochInfo` MUST be converted to an `EpochSummary` and appended to the `summaries` vec.

### Ordering Invariant

Summaries MUST be ordered by epoch number in ascending order. Since epochs advance sequentially (epoch N is always followed by epoch N+1), appending to the vec naturally maintains this ordering.

### Append-Only Guarantee

Within a single session (lifetime of the `EpochManager` instance):

- Summaries are NEVER removed from the vec.
- Summaries are NEVER reordered.
- New summaries are ONLY added via `advance_epoch()`.

### Query Support

The ordered, append-only nature of the summaries vec enables:

- `get_epoch_summary(epoch)` — linear search or direct index lookup.
- `recent_summaries(n)` — slice from the tail of the vec.
- `total_stats()` — iterate all summaries for aggregation.

## Acceptance Criteria

- [ ] Completed epochs are archived as `EpochSummary` in `summaries`.
- [ ] Summaries are ordered by epoch number (ascending).
- [ ] Summaries are append-only (never removed or reordered within a session).
- [ ] `recent_summaries` returns from the tail of the vec.
- [ ] Each `advance_epoch()` call adds exactly one summary.
- [ ] Summary epoch numbers are consecutive.

## Implementation Notes

- The vec is the simplest data structure that satisfies the ordering and append-only requirements.
- No cap on history size is defined in this requirement. If memory becomes a concern, a pruning strategy could be added in a future requirement.
- The append-only guarantee means the vec can be used as a simple log.
