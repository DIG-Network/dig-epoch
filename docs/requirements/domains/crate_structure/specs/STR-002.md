## Summary

The dig-epoch crate organizes its source code into a flat module structure with a single `types/` subdirectory. Each module has a clear, non-overlapping responsibility: constants definition, type definitions grouped by concern, stateless arithmetic, phase calculation, reward computation, epoch management, verification operations, DFSP processing, and error types.

## Specification

The crate MUST include the following source files and modules:

**Root-level modules:**

```
src/
  lib.rs                  # Crate root with public re-exports
  constants.rs            # All epoch constants (CON-001 through CON-005)
  arithmetic.rs           # Height-epoch mapping functions (10 pure functions)
  phase.rs                # Phase calculation (l1_progress_phase_for_network_epoch)
  rewards.rs              # Reward computation functions (5 functions)
  manager.rs              # EpochManager struct and all methods
  verification.rs         # Epoch block root, inclusion proofs, checkpoint data
  dfsp.rs                 # DFSP epoch-boundary functions
  error.rs                # EpochError, CheckpointCompetitionError
  types/
    mod.rs                # Types module re-exports
    epoch_phase.rs        # EpochPhase enum, PhaseTransition struct
    epoch_info.rs         # EpochInfo struct (mutable epoch state)
    epoch_summary.rs      # EpochSummary struct (immutable archive)
    dfsp.rs               # DfspCloseSnapshot, DfspExecutionStageV1, burn policy types,
                          #   proof evaluation context, issuance preview
    events.rs             # EpochEvent enum, EpochStats struct
    checkpoint_competition.rs  # CheckpointCompetition, CompetitionStatus
    reward.rs             # RewardDistribution struct
    verification.rs       # EpochCheckpointData, EpochBlockLink
```

**Module responsibilities:**

| Module | Responsibility |
|--------|---------------|
| `constants.rs` | Compile-time constant definitions only; no functions, no types |
| `types/epoch_phase.rs` | `EpochPhase` enum with `index()`, `next()`, `previous()`, `name()`, permission methods |
| `types/epoch_info.rs` | `EpochInfo` struct with `new()`, `calculate_phase()`, `record_block()`, `set_checkpoint()`, helpers |
| `types/epoch_summary.rs` | `EpochSummary` struct; created from `EpochInfo` on epoch archival |
| `types/dfsp.rs` | All DFSP epoch-boundary type definitions (7 types from SPEC Section 3.14) |
| `types/events.rs` | `EpochEvent` enum (4 variants), `EpochStats` struct |
| `types/checkpoint_competition.rs` | `CheckpointCompetition` struct with competition lifecycle methods, `CompetitionStatus` enum |
| `types/reward.rs` | `RewardDistribution` struct |
| `types/verification.rs` | `EpochCheckpointData` with `hash()` and `test_coin_id()`, `EpochBlockLink` |
| `arithmetic.rs` | 10 pure functions for height-epoch mapping (no EpochManager dependency) |
| `phase.rs` | `l1_progress_phase_for_network_epoch()` free function |
| `rewards.rs` | `block_reward_at_height()`, `total_block_reward()`, `proposer_fee_share()`, `burned_fee_remainder()`, `compute_reward_distribution()` |
| `manager.rs` | `EpochManager` with interior mutability via `RwLock`, all lifecycle methods |
| `verification.rs` | `compute_epoch_block_root()`, `epoch_block_inclusion_proof()`, `compute_epoch_withdrawals_root()`, checkpoint signing material functions |
| `dfsp.rs` | Burn policy, operations digest, commitment digest, namespace rollup, tail roots, activation control |
| `error.rs` | `EpochError`, `CheckpointCompetitionError` with `thiserror` derives |

## Acceptance Criteria

- All listed source files exist in the correct paths
- `cargo check` resolves all module declarations
- No circular dependencies between modules
- `types/` modules contain only type definitions and their inherent methods
- Root-level modules contain free functions and the `EpochManager` struct
- `constants.rs` contains only `pub const` declarations

## Implementation Notes

- The `types/mod.rs` file should re-export all types from its submodules for cleaner internal imports
- Root-level `verification.rs` and `types/verification.rs` are distinct modules: the root module contains free functions using Chia crates, while the types module contains data structures
- Root-level `dfsp.rs` and `types/dfsp.rs` are distinct: the root module contains processing functions, while the types module contains type definitions
- `arithmetic.rs` functions have no dependency on `EpochManager` or any mutable state, enabling use by light clients
